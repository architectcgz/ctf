# 数据库事务管理模式

> 状态：Current
> 事实源：`code/backend/internal/module/*/ports/`、`code/backend/internal/module/*/infrastructure/`、`code/backend/internal/module/architecture_test.go`
> 替代：无

## 定位

本文档说明后端当前数据库事务边界、Transaction Runner 命名、事务内 outbox 和状态机 CAS 写入模式。

- 覆盖：`WithinXxxTransaction` runner、事务 scoped repository、contest 状态推进、outbox 强副作用和架构测试 guardrail。
- 不覆盖：每张表的 DDL；数据库表结构见 `docs/architecture/backend/02-database-design.md`。

## 当前设计

- `code/backend/internal/module/*/ports/`
  - 负责：用显式 port 表达事务能力，例如 `WithinScoringTransaction`、`WithinServiceCheckTransaction`、`WithinAttackLogTransaction`、`WithinRoundReconcileTransaction`、`WithinRoundServiceWritebackTransaction`、`WithinAnnouncementTransaction`、`WithinChallengeImportTransaction`、`WithinAWDChallengeImportTransaction` 和 `WithinChallengePackageExportTransaction`。
  - 不负责：向 application 暴露 `*gorm.DB` 或让 use case 自己拼事务闭包。

- `code/backend/internal/module/contest/infrastructure/submission_repository.go`、`awd_repository.go`、`participation_repository.go`
  - 负责：在 infrastructure 层调用 `db.WithContext(ctx).Transaction(...)`，并把事务内 repository 能力传给 application callback。
  - 不负责：让普通 repository 方法临时开启未命名事务；需要事务时必须形成 reviewed boundary。

- `code/backend/internal/module/contest/infrastructure/contest_status_update_repository.go`
  - 负责：竞赛状态推进使用 `id + status + status_version + deleted_at IS NULL` 做 compare-and-set；同一数据库事务内更新 `contests.status_version`、写入 `contest_status_transitions`，必要时同时 enqueue `contest_realtime_outbox`。
  - 不负责：把状态推进拆成“先改状态、后补 transition”的非原子流程。

- `code/backend/internal/platform/events/outbox_repository.go` 与模块 repository 的 `EnqueueOutboxEvent()` / `EnqueueRealtimeRelay()`
  - 负责：强 side effect 在当前事务内写 outbox；enqueue 失败返回错误并让业务写入回滚。
  - 不负责：替弱事件提供重试；弱事件策略见 `事件发布与降级策略.md`。

- `code/backend/internal/module/architecture_test.go`
  - 负责：检测普通 repository 中未 reviewed 的 `.Transaction()` 使用；显式 `Within*Transaction` 或 `Within*Tx` 命名被视为事务边界。
  - 不负责：证明每个事务的业务不变量都充分；复杂事务仍需模块测试覆盖。

## 边界

- Application 只依赖事务 port，不直接依赖 GORM。
- Infrastructure 是打开数据库事务的 owner；事务闭包内只能暴露当前 use case 需要的 repository 能力。
- 状态机、计分、公告、AWD 轮次写回、题包导入 / 导出这类跨多表写入必须有显式事务边界。
- 读模型聚合不因为查询多表就自动进入写事务；教师聚合查询仍由 query repository owner 控制。

## 接口或数据影响

- `contests.status_version` 是竞赛状态 CAS 的版本号，`contest_status_transitions(contest_id, status_version)` 是迁移历史唯一键。
- `contest_realtime_outbox` 与 `platform_event_outbox` 在需要强 side effect 时必须和业务写入同事务提交。
- 事务 runner 不改变 HTTP DTO 或 OpenAPI 契约；它改变的是 application 与 repository 的依赖方向和失败原子性。

## 历史迁移

- 当前默认不是“任意 repository 方法都可随手开事务”。新增事务必须通过显式 owner、端口命名和架构测试 review。
- 事务文档只记录模式；最终 SQL 与索引仍以 migrations 和模型为准。
