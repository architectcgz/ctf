# 容器调度与并发控制

> 状态：Current
> 事实源：`code/backend/internal/module/practice/application/commands/`、`code/backend/internal/module/container_runtime/application/commands/`、`code/backend/internal/module/instance/application/commands/`
> 替代：无

## 定位

本文档说明后端当前实例调度、容器创建并发控制、失败补偿、runtime node failover 和 AWD desired reconcile 的边界。

- 覆盖：practice provisioning scheduler、`ProvisioningService.CreateTopology()`、Redis 调度锁、runtime node 健康过滤、AWD placement 和启动恢复协作。
- 不覆盖：Docker 网络子网分配细节；子网策略见 `网络子网分配策略.md`。

## 当前设计

- `code/backend/internal/module/practice/application/commands/instance_provisioning_scheduler.go`
  - 负责：在后台循环中领取 `pending` 实例，受 `container.scheduler.max_concurrent_starts`、`max_active_instances` 和 Redis `ctf:practice:instance:scheduler:lock` 保护；拿到锁的 API 副本才会推进 provisioning。
  - 不负责：让 HTTP 请求长时间持有 Docker 冷启动，或引入独立外部队列；排队事实仍在 `instances` 表。

- `code/backend/internal/module/practice/application/commands/runtime_container_create.go`
  - 负责：构造 `TopologyCreateRequest`，写入 `SubnetPool`、`RuntimeNodeID`、AWD stable network、entry port、flag 和 workspace companion 需求。
  - 不负责：直接调用 Docker SDK；运行时执行通过 `container_runtime` capability。

- `code/backend/internal/module/container_runtime/application/commands/provisioning_service.go`
  - 负责：在 `CreateTopology()` 内先保留 host port，再创建 Docker network，随后创建容器、连接网络、下发 ACL；任一阶段失败都会调用 `cleanupTopologyResources()` 清理已创建容器 / 网络，并释放端口和 owner subnet。
  - 不负责：决定业务实例是否允许启动、队伍是否可访问或竞赛是否处于可启动状态。

- `code/backend/internal/module/container_runtime/application/node_health_service.go`、`code/backend/internal/app/composition/runtime_node_failover.go`
  - 负责：通过 runtime node health probe 维护 `runtime_nodes.health_status / last_seen_at / capacity_snapshot`；离线 node 上未过期的 `creating / running` 普通实例会清空旧 runtime identity 后回到 `pending`，由 scheduler 在健康 node 上重建完整拓扑。
  - 不负责：跨宿主迁移单个容器、保持 TCP 会话或把一个拓扑拆到多个 Docker Engine。

- `code/backend/internal/module/practice/application/commands/awd_desired_runtime_reconciler.go`
  - 负责：在 AWD `running / frozen` 比赛中按 `team × visible service` 收敛期望运行态，复用已有实例行和 nonce；失败 scope 写入 Redis backoff / suppress 状态，恢复后清理。
  - 不负责：绕过 contest runtime placement 把同一 AWD contest 的服务静默改绑到其他 runtime node。

- `code/backend/internal/module/instance/application/commands/startup_runtime_recovery_service.go`
  - 负责：进程启动后通过 `ctf:platform:runtime:recovery:lock` 选出 recovery leader；宿主 boot identity 变化时先顺延 active AWD 比赛暂停时长，再执行 `ReconcileLostActiveRuntimes()` 和 `ReconcileDesiredAWDInstances()`。
  - 不负责：把同 boot id 的 heartbeat gap 当成 runtime outage，也不提供管理员手动暂停状态机。

## 边界

- `practice` 拥有“实例何时从 `pending` 进入 `creating`”的业务调度权。
- `container_runtime` 拥有 Docker network / container / ACL 的创建与清理 primitive。
- `instance` 拥有 runtime identity 修复、proxy ticket、maintenance 和 startup recovery。
- `contest` 拥有 AWD 比赛状态、runtime placement 和轮次时间窗；AWD scope 绑定 node 不健康时等待 / backoff，不回退到默认 selector。
- 调度锁只保证多 API 副本下单 owner 推进；数据库状态和 runtime cleanup 仍必须可幂等重试。

## 接口或数据影响

- `instances.status` 承载 `pending / creating / running / failed / expired / stopping` 等实例生命周期，`runtime_node_id / container_id / network_id / runtime_details / access_url` 是执行面 identity。
- `runtime_nodes.last_seen_at`、`health_status` 和 `schedulable` 决定默认 selector 能否接收新实例。
- `contest_runtime_placements` 记录 AWD contest 当前 active runtime node；同一 contest 只允许一个 active placement。
- Redis keys 包括 `ctf:practice:instance:scheduler:lock`、`ctf:container:cleanup:lock`、`ctf:platform:runtime:recovery:lock` 和 `ctf:awd:desired_reconcile:state:<contest_id>:<team_id>:<service_id>`。

## 历史迁移

- 当前运行面是数据库持久化排队 + 后台 scheduler + Docker/runtime-agent capability，不是 Redis list 队列、Swarm、Kubernetes 或跨 node overlay 调度。
- 多 runtime node 只表示多个完整拓扑可以分布到不同宿主；单个拓扑内部不跨 node。
