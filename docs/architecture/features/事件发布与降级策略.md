### 双轨事件发布策略

CTF 后端采用双轨事件发布策略，根据事件重要性选择不同发布模式：

#### 1. 强事件（Strong Events）

**定位**：必须投递的关键事件，发布失败会阻塞业务流程。

**实现机制**：
- 使用 Event Outbox 模式
- 通过 `platform_event_outbox` 表持久化事件
- 后台 worker 定期扫描并投递未发送事件
- 保证至少一次投递（at-least-once delivery）

**适用场景**：
- 影响用户核心流程的事件（如用户注册完成、订单状态变更）
- 影响数据一致性的事件（如积分变更、资源分配）
- 需要跨模块强一致性的事件

**代码位置**：
- Outbox 表定义：`code/backend/migrations/000018_create_platform_event_outbox.up.sql`
- Outbox 实现：`code/backend/internal/platform/events/outbox.go`

#### 2. 弱事件（Weak Events）

**定位**：尽力投递的非关键事件，发布失败仅记录日志，不阻塞业务。

**实现机制**：
- 使用 `publishWeakEvent` 方法直接调用 `eventBus.Publish()`
- 发布失败时记录 warn 级别日志，包含事件名和错误信息
- 不进行重试，不影响业务流程继续执行

**实现模式**（以 SubmissionService 为例）：
```go
func (s *SubmissionService) publishWeakEvent(ctx context.Context, evt platformevents.Event) {
    if s == nil || s.eventBus == nil {
        return // 静默降级：eventBus 未配置时直接返回
    }
    if err := s.eventBus.Publish(ctx, evt); err != nil {
        s.log.Warn("publish_contest_event_failed", 
            zap.String("event", evt.Name), 
            zap.Error(err))
    }
}
```

**适用场景**：
- 统计更新事件（如提交计数、访问记录）
- 缓存刷新事件（如排行榜更新、公告刷新）
- 消费方有兜底机制的事件（如定时重建、轮询拉取）
- 辅助功能事件（如通知推送、日志聚合）

**代码位置**：

### 决策规则

如何判断一个事件应该使用强事件还是弱事件：

| 判断维度 | 强事件 | 弱事件 |
|---------|-------|-------|
| 影响核心流程 | 是 | 否 |
| 影响数据一致性 | 是 | 否 |
| 消费方有兜底机制 | 否 | 是 |
| 发布失败影响用户 | 是 | 否 |
| 需要严格顺序保证 | 是 | 否 |

**示例决策**：

- ✅ 强事件：用户完成 Challenge 解题（影响积分、排行榜、进度）
- ❌ 弱事件：提交记录统计更新（定时任务会重建统计）
- ✅ 强事件：Contest 状态变更（影响所有参赛队伍的可见性）
- ❌ 弱事件：实时排行榜缓存刷新（前端轮询会拉取最新数据）

### 降级机制

#### 1. eventBus 未配置时的静默降级

```go
if s == nil || s.eventBus == nil {
    return // 静默返回，不记录日志
}
```

**场景**：
- 本地开发环境未启动消息队列
- 测试环境使用 mock eventBus
- 单元测试中不依赖真实事件总线

**效果**：业务流程正常执行，事件静默丢弃。

#### 2. 发布失败时的 warn 降级

```go
if err := s.eventBus.Publish(ctx, evt); err != nil {
    s.log.Warn("publish_contest_event_failed", 
        zap.String("event", evt.Name), 
        zap.Error(err))
}
```

**场景**：
- 消息队列不可用（如 Redis 连接中断）
- 事件序列化失败
- 网络超时

**效果**：记录 warn 日志，业务流程继续执行，不影响用户。

### 监控与运维

#### 日志标签

弱事件发布失败时，日志记录以下字段：
- `level`: `warn`
- `message`: `publish_contest_event_failed` 或对应模块的标签
- `event`: 事件名称（如 `contest.submission.scored`）
- `error`: 错误详情

#### 运维建议

1. **监控弱事件发布失败率**：
   - 正常情况下应接近 0%
   - 如果失败率持续升高，需排查事件总线健康状态

2. **检查消费方兜底机制**：
   - 确认消费方有定时重建、轮询拉取或其他恢复手段
   - 弱事件丢失不应导致数据永久不一致

3. **评估事件重要性变化**：
   - 如果某个弱事件的业务重要性提升，考虑升级为强事件
   - 升级时需要引入 Outbox 模式，确保投递保证

## Guardrail

- 新增事件发布时，必须明确选择强事件或弱事件，并在代码 review 中说明理由
- 使用 publishWeakEvent 的场景，必须确认消费方有兜底机制
- 升级弱事件为强事件时，必须引入 Outbox 持久化，不能只改日志级别

## 已知限制

- 当前 publishWeakEvent 不进行重试，未来可考虑引入有限次数的本地重试
- 弱事件丢失后无法恢复，依赖消费方的定时重建或轮询机制
- 没有统一的弱事件发布失败率监控，需要运维侧手动配置日志告警
