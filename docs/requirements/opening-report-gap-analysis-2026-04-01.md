# 开题报告对照缺口分析（2026-04-01）

## 目的

将 `docs/开题报告/开题报告.md`、`docs/毕业设计课题.md` 与当前代码、接口、文档现状做一次面向毕设验收的对照，回答两个问题：

1. 哪些能力已经可以算“完成”。
2. 哪些能力虽然已有代码，但还不足以支撑中后期答辩与论文论证。

本文不做新的范围扩张，默认以开题报告承诺为上位约束。

## 总结结论

当前平台的主业务链已经明显超过“项目骨架”阶段，训练、Jeopardy 竞赛、队伍、冻结榜、能力画像、推荐、报告导出、教师分析、通知、AWD 运维与流量采集都已经落地。

如果只看“有没有功能”，开题报告中的大多数核心模块已经具备。

如果按“是否足够支撑毕业设计答辩”来判断，当前真正还缺的重点不是再补很多散点页面，而是以下三类收口：

1. 实时排行榜/WebSocket 推送的端到端闭环证据仍然不足。
2. 性能、安全隔离、长稳与故障注入的实验验证材料明显不足。
3. 部分设计文档里的目标能力还停留在设计口径，代码中没有对应实现闭环，尤其是竞赛类实时推送、镜像构建/拉取流水线、镜像扫描等。

## 一、已完成或基本完成

### 1. 用户认证与 RBAC

- 开题目标：管理员、教师、学生差异化权限控制。
- 现状判断：已完成。
- 证据：
  - 路由已按管理员、教师/管理员、普通用户分组。
  - 教师录题、管理员运维、学生训练/竞赛访问边界已分离。

### 2. 靶场管理主链路

- 开题目标：题目、镜像、难度/标签、附件、Writeup 管理。
- 现状判断：基本完成。
- 证据：
  - 题目、镜像、题解、拓扑、环境模板、Flag 配置、题目发布、自测接口均已存在。
  - 题目包导入已支持预览、提交、按 `package_slug` 稳定 upsert，并覆盖静态/动态/正则/manual_review 等判题配置。

### 3. 攻防演练主链路

- 开题目标：实例启动、访问、续期、回收、Flag 提交、计分。
- 现状判断：已完成。
- 证据：
  - 用户可启动练习实例与竞赛实例。
  - 已有实例生命周期与异步更新能力。
  - 已有提交判题、积分更新、Hint 解锁与时间线记录。

### 4. Jeopardy 竞赛主链路

- 开题目标：竞赛创建、队伍管理、排行榜、冻结榜。
- 现状判断：基本完成。
- 证据：
  - 已有竞赛增删改查、题目入赛、报名审核、公告、队伍创建/加入/退出/踢人。
  - 已有排行榜查询与冻结/解冻逻辑。
  - 已有赛事结果导出接口。

### 5. 技能评估与教学闭环

- 开题目标：能力画像、推荐练习、报告导出。
- 现状判断：已完成，且实际完成度较高。
- 证据：
  - 已有能力画像重建/增量更新。
  - 已有薄弱维度识别与推荐题目。
  - 已有个人报告、班级报告、比赛导出、学生复盘归档导出与完整查看页。
  - 教师侧已有班级概览、趋势、复盘建议、学生证据页与时间线页。

### 6. 容器基础设施与隔离落地

- 开题目标：容器生命周期、网络与资源隔离、最小权限。
- 现状判断：基本完成。
- 证据：
  - 运行时配置已支持 CPU、内存、PIDs、只读根文件系统、运行用户、能力集、seccomp。
  - 实例创建时已创建独立网络并在失败时清理。
  - 运行时已支持向容器写入 Flag 文件。
  - 已有网络隔离与运行时相关测试。

### 7. 动态 Flag 与基础反作弊

- 开题目标：动态 Flag、频率限制、审计记录。
- 现状判断：基本完成。
- 证据：
  - 已有动态 Flag 配置与校验入口。
  - 已有 rate limit、audit logs、cheat-detection 管理接口。
  - 已有动态 Flag、审计、作弊检测相关集成测试。

### 8. AWD 扩展

- 开题口径：一期聚焦训练 + Jeopardy，AWD 预留扩展。
- 现状判断：已超过“仅预留”阶段，做到了一定可用深度。
- 证据：
  - 已有 AWD 轮次、服务检查、攻击日志、流量事件、轮次摘要、攻防计分同步、Flag 注入、榜单支持。

## 二、部分完成但答辩还不稳

### 1. 实时排行榜“有榜单，但 WebSocket 推送闭环证据不足”

- 开题报告明确写了“通过 WebSocket 获取实时得分与排名变动”“通过 WebSocket 推送排名与得分变动”。
- 当前代码里明确落地的 WebSocket 入口是 `/ws/notifications`，用于通知推送。
- 目前未看到与排行榜变动直接对应的后端 WebSocket 路由、消息协议、前端订阅链路和联调证据。
- 结论：
  - 排行榜功能本身已完成。
  - “实时榜单通过 WebSocket 推送”这一承诺，目前更像设计目标，不宜在答辩中表述为已完整实现。

### 2. 攻击过程记录已具备雏形，但口径应表述为“证据链/时间线”，不要夸大成全流量回放

- 当前已存在：
  - 学生时间线。
  - 教师证据页。
  - 复盘归档中整合 timeline、evidence、writeup、人工评语。
- 但记录的主要是：
  - 访问实例。
  - 平台代理请求。
  - 提示解锁。
  - 提交结果。
- 这足够支撑“教学复盘证据链”，但还不足以表述成“完整漏洞利用全过程自动回放”。
- 结论：
  - 功能上可以说已满足课题要求的教学记录方向。
  - 论文/答辩时应强调“关键行为证据链”，不要表述成 IDS/全流量取证系统。

### 3. 镜像管理已可用，但更像“登记/校验现有镜像”，不是完整镜像供应链

- 当前镜像管理支持新增、更新、删除，创建时会校验 Docker 本地镜像是否可访问并记录大小。
- 但未看到完整的：
  - Dockerfile 在线构建。
  - Registry 拉取任务。
  - 构建日志。
  - 镜像扫描任务。
- 结论：
  - 若按开题报告“镜像管理”字面要求，当前可勉强成立。
  - 若按更强工程口径解释成“镜像构建与交付平台”，当前还不够。

### 4. 反作弊属于“基础机制已具备”，但缺少更强的论文化验证材料

- 代码层面已有动态 Flag、频率限制、审计记录、作弊检测页。
- 但若要支撑论文中的“机制有效性”，还需要：
  - 典型作弊样本。
  - 检出示例。
  - 误报/漏报边界说明。
- 结论：
  - 不一定缺功能。
  - 缺实验与论证材料。

## 三、当前最明确的缺口

### 1. 性能、长稳、故障注入、安全隔离验证报告缺失

- 开题报告第三部分明确写了：
  - 并发压测。
  - 长稳运行。
  - 故障注入。
  - 安全隔离测试。
- 当前 `docs` 下主要是架构设计、契约、评审、任务拆解和功能设计文档。
- 我没有看到独立的、可直接用于论文或答辩的：
  - 压测报告。
  - 长稳运行记录。
  - 故障注入记录。
  - 隔离验证实验报告。
- 这是目前最需要补的答辩材料型缺口。

### 2. 实时 WebSocket 榜单推送没有足够实现证据

- 这是开题报告中写得很明确的一项技术方案。
- 当前 WebSocket 实现证据集中在通知系统，不在竞赛实时榜单。
- 若不补实现，至少要在论文中收缩表述，改成“预留并已完成通知推送基础设施，榜单当前采用高频拉取/查询模式”。

### 3. 设计文档中的部分高阶安全能力尚未在代码中闭环

- 文档里有较强的设计目标，例如：
  - 竞赛公告 WebSocket 推送。
  - 镜像扫描。
  - 更完整的镜像/导入安全流水线。
- 当前代码与接口证据不足。
- 这些不一定都要做成毕业设计必做项，但必须避免把“设计目标”当成“已实现能力”写进论文正文。

## 四、按毕设视角的最终判断

如果你的目标是“先保证毕业设计能过，并且答辩口径稳”，我建议把当前状态定义为：

1. 主业务功能已经基本达到开题报告承诺。
2. 最欠缺的不是再堆新功能，而是补实验验证与收口证据。
3. 若只能继续做少量关键工作，优先级应是：
   - P1：补性能/隔离/稳定性实验与报告。
   - P1：补实时排行榜 WebSocket 推送，或者明确降级口径并统一论文表述。
   - P2：把反作弊、安全边界、AWD 流量监控整理成可展示的实验样例。
   - P3：是否补镜像构建/扫描流水线，取决于时间；这更像“工程增强项”，不是当前最关键的答辩阻塞项。

## 五、建议的答辩口径

- 可以强讲：
  - 训练、竞赛、评估三位一体闭环。
  - 容器隔离、动态 Flag、队伍竞赛、冻结榜、能力画像、推荐、教学复盘归档。
  - AWD 已有扩展性实现，不只是预留接口。
- 需要谨慎讲：
  - 排行榜 WebSocket 实时推送。
  - 镜像构建/镜像扫描。
  - 反作弊机制“效果显著”的结论。
- 必须补证据再讲：
  - 并发压测结论。
  - 长稳运行结论。
  - 故障注入恢复能力。
  - 安全边界有效性实验结果。
