## 1. 管理面网络和靶机网络分离

平台服务、数据库、Redis、Docker 管理能力属于**管理面**；题目容器属于**靶机运行面**。你的设计目标是：学生即使通过题目漏洞进入靶机容器，也不能直接访问平台 API、PostgreSQL、Redis、Docker socket 或宿主机敏感端口。论文表 3.1 里已经明确把“靶机容器内命令执行后尝试访问平台内部服务”列为威胁，并把“容器不能直接访问 PostgreSQL、Redis、Docker socket 和后端管理接口”作为安全目标。

面试回答时不要说“Docker 天然隔离”，这会被打。你要说：

> Docker 只是运行载体，不是强安全边界。我的隔离目标是降低靶机容器接触管理面的可能性，并通过网络不可达、凭证短时化和资源限制缩小风险窗口。

## 2. 普通训练实例默认独立网络

普通训练题不是 AWD，不需要学生之间互相攻击，所以默认策略应该是**同题不同学生实例之间互不可达**。论文里写的是：普通训练实例默认使用独立网络，避免不同用户实例互访；平台服务所在网络不暴露给靶机容器；容器只映射题目需要的端口。

你可以这样展开：

> 单容器题目会给每个实例分配独立的小网段，当前设计用 `10.11.0.0/16` 按 `/29` 切分。`/29` 每个子网可用地址少，但对单容器题够用，优点是可切出更多实例网络，减少不同学生容器之间的横向移动面。多容器 topology 题使用 `10.10.0.0/16` 按 `/24` 切分，因为多容器题需要容纳多个节点、别名和内部访问关系，所以需要更大的子网。配置加载时会做 CIDR 合法性和重叠检查，避免 Docker 网络冲突。

这里老师可能追问：**为什么单容器用 /29，多容器用 /24？**

你答：

> `/29` 适合单容器题，因为地址空间小、可切分数量多，能支持更多并发实例；`/24` 适合多容器拓扑题，因为同一个题目内部可能有 Web、DB、内网服务、攻击机等多个容器，需要更多地址、网络别名和 ACL 规则空间。两者分池可以避免为了少数 topology 题把所有单容器实例都浪费在大网段里。

## 3. 访问入口不直接暴露容器真实地址

论文中这点很重要：普通 HTTP 靶机访问时，学生不是直接获得容器真实地址，而是请求实例访问接口，由后端校验实例所有权和竞赛上下文，再签发短时 `proxy ticket`，代理层再按 ticket 中的信息转发请求。AWD 攻击访问还会携带攻击方队伍、受害方队伍和服务标识。

面试中你应该这样讲：

> 访问代理的作用不是单纯反向代理，而是把访问控制前置到每一次靶机访问之前。学生不能自己拼容器 IP 或端口访问别人的实例；他必须先通过后端校验“这个实例是不是他的、比赛上下文是否允许访问、ticket 是否过期”。这样可以降低容器真实地址泄露、URL 长期复用和越权访问风险。

老师可能追问：**TCP 服务怎么办？**

你可以答：

> HTTP 服务可以统一走代理和短时 ticket；原生 TCP 服务目前会返回带协议标记的访问地址，这一块安全边界弱于 HTTP 代理，所以需要通过端口分配、实例所有权校验、短时开放窗口、防火墙规则或后续的 TCP proxy 继续增强。论文里也把完整强隔离和更复杂访问治理作为后续增强方向，而不是声称已经做到生产级零信任访问。

## 4. AWD 场景是“受控互通”，不是完全隔离

AWD 和普通训练不同。普通训练要求学生之间互相隔离；AWD 要求队伍之间能按规则攻击，否则比赛无法进行。你的论文写得比较准确：AWD 网络需要在“允许对抗”和“隔离管理面”之间找平衡，不能直接复用平台内部网络，而是借助单独网络、服务别名和 ACL 表达允许访问对象。

答辩时可以这样说：

> AWD 中不能简单地“一刀切隔离”，因为队伍 A 必须能够访问队伍 B 的目标服务，checker 也必须能访问各队服务。所以 AWD 使用单独赛级网络，把队伍服务放到比赛网络里，通过服务别名和 ACL 限定可访问对象。这个网络只承载比赛流量，不承载平台 API、数据库、Redis 和 Docker 管理接口。也就是说，AWD 允许的是“比赛规则内的服务互通”，不是“容器对平台管理面的互通”。

老师可能追问：**如果队伍 A 扫描整个 AWD 网段怎么办？**

你答：

> 这是 AWD 场景的现实风险。当前设计通过 ACL、服务别名、最小端口暴露和流量事件记录来约束与追踪；平台只开放比赛需要的服务端口，不开放管理面。扫描行为可以进入 `awd_traffic_events` 做复盘或告警。但我不会声称它完全防止所有横向探测，尤其是在同一赛级网络内，强隔离还需要更细粒度的网络策略，例如基于 iptables/nftables、CNI network policy 或 eBPF 的队伍级访问控制。

## 5. 运行时权限和资源限制配合网络隔离

网络隔离不是单独成立的。你的论文还写了默认关闭特权模式、收缩 Linux Capabilities、CPU/内存/PIDs 配额，Docker socket 不挂入靶机容器，安全验证中检查了样本容器非特权、管理面服务名默认不可达、Docker socket 未暴露、AWD 互通仅发生在赛级网络。

你可以这样总结：

> 网络隔离解决“能不能连到不该连的对象”；最小权限解决“容器里拿到执行能力后能不能进一步提升权限”；资源限制解决“能不能用 fork bomb、内存占满或 CPU 打满拖垮宿主机”；生命周期清理解决“异常容器和网络会不会长期残留”。这几个机制必须一起讲，单讲 Docker network 是不够的。

## 网络方向面试高频问题 + 推荐答案

### 1. Docker 默认 bridge 网络有什么问题？为什么不用默认 bridge？

**推荐回答：**
 默认 bridge 容易让同一 bridge 上的容器彼此可达，不适合多学生靶机隔离。我的设计是为训练实例创建独立网络，并按实例或 topology 分配子网，避免不同用户实例默认互通。普通训练场景中，学生没有攻击其他学生容器的业务需求，所以默认应该互相隔离。

### 2. 你的系统怎么防止学生从靶机容器访问 PostgreSQL 或 Redis？

**推荐回答：**
 数据库和 Redis 在平台管理面网络中，靶机容器不加入该网络，也不暴露管理面服务名和端口。普通训练容器使用独立实例网络；AWD 使用单独赛级网络，也不复用平台内部网络。安全验证里还做了管理面服务名默认不可达、Docker socket 未挂入靶机容器等检查。

### 3. 如果题目容器里能执行 `curl ctf-api:8080`，会发生什么？

**推荐回答：**
 正常设计下应该解析不到或访问不到，因为平台 API 不在靶机网络内。如果能访问到，说明管理面网络被错误加入题目容器，属于严重隔离缺陷。我的验证目标之一就是保证靶机容器不能直接访问后端 API、PostgreSQL、Redis 和 Docker socket。

### 4. 你为什么还需要 proxy ticket，直接端口映射不行吗？

**推荐回答：**
 直接端口映射只能证明服务可访问，不能证明访问者有权限。proxy ticket 可以把访问行为和用户、实例、比赛上下文绑定起来。访问前后端会检查所有权或比赛规则，然后签发短时 ticket；代理层再根据 ticket 转发。这样避免容器地址长期暴露，也降低旧链接、伪造入口和越权访问风险。

### 5. WebSocket ticket 和 proxy ticket 有什么区别？

**推荐回答：**
 WebSocket ticket 用于实时连接握手，解决长连接不能暴露长期 token 的问题；proxy ticket 用于靶机访问，解决访问容器前的所有权校验和短时授权问题。两者都是短时票据，但绑定的业务对象不同：WebSocket 绑定用户和通道，proxy ticket 绑定用户、实例、竞赛和访问目的。论文里也明确 WebSocket 握手和实例访问都采用短时 ticket。

### 6. AWD 里面为什么不能完全隔离队伍网络？

**推荐回答：**
 AWD 的业务规则要求队伍之间能攻击服务，checker 也要检查各队服务。如果完全隔离，攻击提交和服务检查都做不了。所以 AWD 采用受控互通：队伍服务进入赛级网络，通过服务别名和 ACL 表达允许访问链路，但平台 API、数据库、Redis、Docker socket 和宿主机敏感端口仍不暴露给参赛容器。

### 7. 你的 ACL 是应用层 ACL 还是网络层 ACL？

**推荐回答：**
 论文里表达的是网络组织和访问规则层面的 ACL，核心是限定 AWD 赛级网络中哪些服务、队伍、端口可以互通。应用层还会通过 proxy ticket 校验攻击方队伍、受害方队伍和服务标识。严格来说，这是网络层隔离和应用层授权的组合；如果要进一步增强，可以落到 iptables/nftables、CNI NetworkPolicy 或 eBPF 层面。

### 8. 为什么单容器实例按 `/29` 切分？

**推荐回答：**
 单容器题通常只需要容器本身、网关和少量保留地址，`/29` 已经足够。相比 `/24`，`/29` 可以从同一个地址池切出更多实例网络，适合班级并发训练。多容器 topology 才用 `/24`，因为它需要多个容器节点、网络别名和 ACL 编排余量。

### 9. 如果两个 Docker 网络 CIDR 重叠会怎样？

**推荐回答：**
 可能导致路由冲突、容器互访异常、Docker 网络创建失败或访问路径不可预测。所以配置加载时要做 CIDR 合法性和重叠检查。论文里已经写了两套地址池会做 CIDR 合法性和重叠检查，避免不同粒度子网混发后撞上 Docker 网络冲突。

### 10. 如何验证网络隔离真的生效？

**推荐回答：**
 可以从容器内执行命令级检查：尝试解析或访问 `ctf-api`、`ctf-postgres`、`ctf-redis`；检查 `/var/run/docker.sock` 是否挂载；检查容器是否 privileged；尝试访问其他普通训练实例；AWD 场景下再验证允许的赛级服务是否可达。论文第 5.5 就做了命令级检查，验证样本靶机容器不是特权容器、管理面服务名默认不可达、Docker socket 未挂入、AWD 互通仅发生在赛级网络。

### 11. 你的隔离能防 Docker escape 吗？

**推荐回答：**
 不能这样承诺。我的设计能降低题目容器访问管理面和滥用资源的风险，但不能证明能抵御内核漏洞、Docker escape 或宿主机 root 级攻击。要进一步增强，需要 gVisor、Kata Containers、Firecracker、独立虚拟机、seccomp/AppArmor、只读根文件系统和镜像扫描等机制。论文里也明确当前隔离边界不能替代完整渗透测试。

### 12. 端口映射会不会造成越权访问？

**推荐回答：**
 会有风险，尤其是原生 TCP 服务。如果宿主机端口长期暴露，其他用户可能绕过平台页面直接访问。因此 HTTP 服务更适合走代理和短时 ticket；TCP 服务需要结合端口随机化、所有权校验、访问窗口、iptables 或 TCP proxy。当前论文已经做了访问票据和所有权校验，但 TCP 访问治理可以作为后续增强点。

## 1. 先纠正一个表达：不是“不用 bridge”，而是“不用默认 bridge”

Docker 的常见网络模式里：

| 说法                      | 含义                                                         | 是否隔离                     |
| ------------------------- | ------------------------------------------------------------ | ---------------------------- |
| 默认 `bridge` / `docker0` | 所有不指定网络的容器都挂在同一个默认 bridge 上               | 隔离弱，同网桥内容器容易互通 |
| user-defined bridge       | 自己 `docker network create` 出来的网络，每个网络有自己的 bridge、子网和 DNS 域 | 不同 Docker network 默认隔离 |
| `none`                    | 容器没有网络栈，只保留 loopback                              | 最强，但题目无法访问         |
| `host`                    | 容器直接使用宿主机网络                                       | 基本无网络隔离               |
| overlay/macvlan           | 多主机或直接接入物理二层网络                                 | 需要额外网络策略             |

所以你论文/答辩里不要说“我不用 bridge”，要说：

> 我不把所有题目容器挂到 Docker 默认的 `bridge/docker0` 上，而是为实例创建独立的 user-defined bridge network。

这个表述才专业。

## 2. `10.11.1.0` 和 `10.11.2.0` 是不是“同一个网段”？

要看**子网掩码**，不能只看前两段。

假如你说的是：

```
实例 A 网络：10.11.1.0/29
实例 B 网络：10.11.2.0/29
```

那它们**不是同一个网段**。它们只是来自同一个大地址池 `10.11.0.0/16`，但被切成了不同的小子网。

`/29` 每个子网 8 个地址，例如：

```
10.11.1.0/29 覆盖：
10.11.1.0 - 10.11.1.7

10.11.2.0/29 覆盖：
10.11.2.0 - 10.11.2.7
```

这两个子网互不重叠。

所以你应该这样解释：

> `10.11.0.0/16` 是地址池，不代表所有容器都在同一个二层网络里。真正决定互通范围的是 Docker network 对象和该 network 的子网配置。每个实例拿到的是一个独立的 `/29` 子网和独立 Docker bridge，不是所有实例共用一个 `10.11.0.0/16` 网络。

## 3. 光是不同 CIDR 就一定隔离吗？

**不一定。**

隔离成立需要同时满足几个条件：

1. 两个容器不在同一个 Docker network；
2. 两个 Docker network 的 CIDR 不重叠；
3. 容器没有同时加入多个网络；
4. 宿主机没有手动配置跨 bridge 转发；
5. iptables/nftables 没有放通跨 Docker bridge 的流量；
6. 目标服务没有通过宿主机端口暴露给所有人；
7. 应用层访问入口还有权限校验，例如 proxy ticket。

也就是说，**CIDR 不重叠只是必要条件之一，不是充分条件。**

更准确的回答是：

> 不同实例是否隔离，核心不取决于它们是不是来自同一个大地址池，而取决于它们是否处于不同 Docker network、宿主机是否允许跨网桥转发，以及是否存在宿主机端口暴露或代理绕过。我的设计是每个普通训练实例一个独立 Docker network，CIDR 从统一地址池切分但互不重叠，同时不把平台管理面网络挂入靶机容器。

## 4. 两个 user-defined bridge 网络为什么默认不能互通？

假设：

```
docker network create --subnet 10.11.1.0/29 inst_a_net
docker network create --subnet 10.11.2.0/29 inst_b_net

docker run --network inst_a_net challenge_a
docker run --network inst_b_net challenge_b
```

Docker 会创建两个不同的 Linux bridge，大致类似：

```
br-aaa  10.11.1.1/29
br-bbb  10.11.2.1/29
```

容器 A 的默认网关是 `10.11.1.1`，容器 B 的默认网关是 `10.11.2.1`。它们不在同一个二层广播域里，ARP 不会直接互通。

如果 A 想访问 B：

```
容器 A -> 网关 br-aaa -> 宿主机路由/iptables -> br-bbb -> 容器 B
```

中间必须经过宿主机转发。Docker 对不同 bridge 网络通常会通过 `DOCKER-ISOLATION` 相关链阻止跨 bridge 转发。也就是说，不是“IP 看起来不同就绝对不通”，而是 Docker bridge 网络 + iptables 隔离规则共同让它默认不通。

但你要注意：如果你在宿主机上手动加了转发规则，或者关闭/改坏了 Docker 的隔离链，就可能打通。

## 5. 哪些情况会破坏隔离？

这些是面试官最可能追问的坑。

### 情况一：两个容器其实挂在同一个 Docker network

如果你创建的是：

```
docker network create --subnet 10.11.0.0/16 ctf_net
docker run --network ctf_net challenge_a
docker run --network ctf_net challenge_b
```

那 A 和 B 就在同一个 Docker network 里，即使 IP 分别是 `10.11.1.2` 和 `10.11.2.2`，它们也属于同一个 `/16` 网络，默认可以互相访问。

所以不能只看 IP，必须看：

```
docker inspect <container>
docker network inspect <network>
```

确认它们是不是同一个 network object。

### 情况二：容器加入了多个网络

如果某个容器同时加入：

```
inst_a_net
platform_internal_net
```

那它就可能成为跳板，突破隔离。你的平台要避免题目容器加入管理面网络。

### 情况三：宿主机端口暴露绕过隔离

即使两个容器网络隔离，如果容器 B 的服务被映射成：

```
0.0.0.0:30080 -> container_b:80
```

那么容器 A 可能通过宿主机 IP + 端口访问 B。
 所以端口映射要谨慎，最好配合访问代理、短时 ticket、防火墙或只绑定本地回环/受控入口。

### 情况四：AWD 场景本来就需要互通

AWD 不能按普通训练那样完全隔离，因为队伍之间要互相攻击。AWD 的正确做法不是“禁止互通”，而是“受控互通”：只开放比赛服务端口，不开放平台管理面。

## 6. 你项目里最严谨的网络隔离表述

你可以把之前的说法改成这个版本：

> 普通训练场景中，平台不使用 Docker 默认 `bridge/docker0` 作为所有靶机的共享网络，而是为每个实例创建独立的 user-defined bridge network。单容器题目从 `10.11.0.0/16` 地址池中切分独立 `/29` 子网，多容器 topology 从 `10.10.0.0/16` 地址池中切分独立 `/24` 子网。这里的 `/16` 只是地址池，不是所有容器共用的单一网络；每个实例网络对应独立 Docker network 和独立 Linux bridge。平台在创建网络前检查 CIDR 合法性和重叠，避免路由冲突。容器只加入题目运行网络，不加入平台 API、PostgreSQL、Redis 或 Docker 管理面网络。HTTP 靶机访问再通过 proxy ticket 和代理层做所有权校验，避免直接暴露容器真实地址。AWD 场景单独使用赛级网络实现规则内互通，但该网络仍与平台管理面隔离。

这段比“两个网段就隔离了”严谨很多。

------

## 7. 面试官追问：“那 10.11.1.0 和 10.11.2.0 不是同一个 10.11.0.0/16 吗？”

你答：

> 它们来自同一个 `/16` 地址池，但不是同一个实际网络。实际创建时不是创建一个 `10.11.0.0/16` 的 Docker 网络，然后把所有容器都放进去；而是从这个地址池切出多个互不重叠的小 CIDR，例如 `10.11.1.0/29`、`10.11.2.0/29`，每个 CIDR 对应一个独立 Docker network。是否互通看 Docker network 对象和宿主机转发规则，而不是只看 IP 前缀相似。

## 8. 面试官追问：“如果宿主机能路由，两个网络还能隔离吗？”

你答：

> 如果宿主机明确放通跨 bridge 转发，那隔离会被破坏。所以我的隔离不是只靠 CIDR，而是靠 Docker user-defined bridge 的网络边界、Docker 的隔离链、防火墙规则、容器不加入多网络、平台管理面不挂入题目网络、访问入口走代理校验这几层共同保证。严格安全场景还应该加 iptables/nftables 明确 DROP 跨实例 bridge 流量，而不是只依赖 Docker 默认行为。

这句话很加分，因为你承认了隔离边界，不吹。
