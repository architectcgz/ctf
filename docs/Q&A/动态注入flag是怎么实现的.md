# Q&A：动态注入 Flag 是怎么实现的？

本文回答 CTF 项目里的“动态注入 Flag”具体是怎么落地的，并区分两种场景：

1. 普通练习/比赛实例启动时，为单个实例生成并注入动态 Flag。
2. AWD 模式下，按轮次为各队正在运行的靶机批量轮换并注入动态 Flag。

关联文档：

- `ctf/docs/contracts/challenge-pack-v1.md`
- `ctf/docs/architecture/backend/03-container-architecture.md`
- `ctf/docs/architecture/backend/05-key-flows.md`
- `ctf/docs/Q&A/AWD攻防模式如何实现与计分.md`

---

## 1. 先说结论

这个项目里的“动态注入 Flag”不是把 Flag 写死在题目源码里，而是由平台在运行时动态生成，再注入到容器里。

当前实现分成两条路径：

- **普通实例模式**：实例启动时生成动态 Flag，主要通过环境变量注入给容器，题目进程从 `CTF_FLAG` 或 `FLAG` 读取。
- **AWD 模式**：每轮重新生成 Flag，并通过 Docker API `CopyToContainer` 把新 Flag 写入运行中容器的 `/flag/flag.txt`。

也就是说：

- “启动即注入”主要靠**环境变量**
- “运行中轮换”主要靠**文件写入**

---

## 2. 普通实例的动态 Flag 是怎么生成的？

普通练习题或非 AWD 竞赛实例，在创建实例时会先生成本实例专属 Flag。

核心做法是：

1. 先生成一个随机 `nonce`
2. 用 `subjectID + challengeID + nonce` 作为消息体
3. 用平台全局密钥做 `HMAC-SHA256`
4. 截取前 32 个十六进制字符，拼成 `flag{...}` 或题目配置的前缀格式

项目里的算法在 `code/backend/pkg/crypto/flag.go`，形式是：

```text
flag = HMAC-SHA256(globalSecret, "userID:challengeID:nonce")
```

再结合题目的 `flag_prefix`，生成类似：

```text
flag{2f3c...}
ctf{2f3c...}
```

这里的关键点是：

- 不把真实 Flag 存数据库明文
- 同一个用户/队伍、同一道题、不同实例会因为 `nonce` 不同而得到不同 Flag
- 判题时只要重新按相同参数计算一次，就能验证提交是否正确

### 2.1 这里的 nonce 是做什么的？

`nonce` 可以理解成动态 Flag 生成里的“变化输入”或“扰动因子”。

它的核心作用是：

- 让同一个用户反复启动同一道题时，不会永远拿到同一个 Flag
- 把 Flag 绑定到“这一次实例”，而不是只绑定到 `userID + challengeID`
- 让服务端只保存 `nonce`，就可以在校验时重新计算期望 Flag，而不必存明文 Flag

如果没有 `nonce`，只靠：

```text
userID + challengeID + secret
```

那么同一个用户多次重启或重建实例，理论上可能得到同一个动态 Flag，这会削弱实例隔离性，也不利于实例回收后的重新发题。

所以在普通实例里，`nonce` 的真实语义是：

> **这个实例专属的随机因子。**

当前项目里它由 `GenerateNonce()` 生成，并保存到 `instances.nonce`。后续用户提交 Flag 时，服务端会取出这个 `nonce`，按同样算法重算，再与提交值比较。

## 3. 普通实例里，Flag 是怎么注入到容器里的？

当前项目的一期主路径是“**创建容器时通过环境变量注入**”。

题目包规范和示例题都按这个约定工作：

- 平台创建实例时，把动态 Flag 放进容器环境变量，例如 `CTF_FLAG`
- 容器内应用启动后读取这个环境变量
- 题目逻辑再决定把它显示在页面上、写入数据库、放入某个业务流程，供选手利用漏洞取出

例如示例题 `web-hello-01`、`web-sqli-login-01` 都是从 `CTF_FLAG` 读取。

这种做法的优点是：

- 实现简单，实例启动时一次注入即可
- 不需要容器启动后再二次写文件
- 对 Web 题、入门题比较友好

它的限制也很明显：

- 环境变量适合“启动时确定”的 Flag
- 不适合 AWD 这种“容器已在运行、每轮都要换 Flag”的场景

---

## 4. AWD 模式下为什么不用环境变量，而改成文件注入？

因为 AWD 的 Flag 是**每轮轮换**的。

如果还靠环境变量，通常意味着：

- 要么重启容器才能换新值
- 要么进入容器执行 shell 命令临时改写

这两种都不理想：

- 重启容器会影响服务连续性
- `sh -c "echo ... > /flag/flag.txt"` 有命令注入风险

所以 AWD 当前采用的是：

- 轮次开始时重新生成每队每题的新 Flag
- 通过 Docker API `CopyToContainer`
- 直接把内容写到容器内 `/flag/flag.txt`

这样做的好处是：

- **不需要重启容器**
- **不经过 shell**
- **可以对运行中靶机做实时轮换**

## 5. AWD 轮换注入的完整链路是什么？

### Step 1：轮次任务构造本轮 Flag

`AWDRoundUpdater` 会先按“队伍 × 题目”构造本轮的 Flag 分配表。

这里不是复用普通实例的随机 `nonce`，而是使用一个**可重建的轮次 nonce**，格式相当于：

```text
awd:{contestID}:{roundNumber}:{teamID}:{challengeID}
```

然后仍然走统一的动态 Flag 生成算法，得到本轮 Flag。

这样做的好处是：

- 同一轮可重复计算、可验证
- 不必把每个队伍每道题的明文 Flag 长久存数据库
- 只要知道比赛、轮次、队伍、题目和全局密钥，就能重建

这里的 `nonce` 和普通实例里的随机 `nonce` 含义不同。

- 普通实例里的 `nonce`：代表“某一次实例”，通常是随机生成的
- AWD 里的轮次 `nonce`：代表“某一轮 + 某一队 + 某一题”，是按上下文可重建的

所以 AWD 不是把 `nonce` 这个概念取消了，而是把它从“实例随机值”换成了“轮次上下文标识”。

### Step 2：先把本轮 Flag 存到 Redis

设计文档约定把当前轮 Flag 放到 Redis Hash，例如：

```text
awd:flags:{contest_id}:{round}
```

目的不是给题目读，而是给**提交流程做 O(1) 校验**，同时支持轮次过期后清理。

### Step 3：定位需要注入的运行中容器

`AWDFlagInjector` 会按 `team_id + challenge_id` 去找目标容器。

当前代码的查找口径是：

- 优先找 `contest_id + team_id` 直接归属该队的运行中实例
- 如果还没有完全切到“团队实例模型”，就回退到“该队成员各自运行中的实例”
- 如果一个实例有多个容器（例如主容器 + sidecar），会把所有容器 ID 收集出来一起注入

所以现阶段的真实语义是：

- **注入目标不是抽象题目记录**
- **而是该队当前正在运行的一个或多个容器**

### Step 4：把 Flag 写进容器文件

运行时模块提供了 `WriteFileToContainer`，底层会：

1. 在内存里构造一个 tar 归档
2. 把 `flag.txt` 放进 tar
3. 调 Docker SDK 的 `CopyToContainer`
4. 将内容写入目标目录

AWD 注入器当前默认写入路径是：

```text
/flag/flag.txt
```

这也是现有 AWD 文档和测试统一使用的路径。

### Step 5：Checker 与提交校验按当前轮工作

轮换后：

- Checker 继续探测服务是否存活
- 攻击提交接口按“当前轮 + victim_team_id + challenge_id”校验 Flag
- 为了避免轮换瞬间的新旧 Flag 竞态，还会允许一个 `previous_round_grace` 的上一轮宽限期

## 6. 当前项目里“动态 Flag 注入”其实有两种注入口径

这是最容易混淆的地方。

### 6.1 环境变量注入

主要用于：

- 普通练习实例
- 题目首次启动时的一次性注入
- challenge-pack 示例题

典型读取方式：

- `CTF_FLAG`
- 兼容别名 `FLAG`

### 6.2 文件注入

主要用于：

- AWD 运行中轮换
- 容器启动后不重启地替换 Flag

典型路径：

- `/flag/flag.txt`

因此你可以把它理解成：

- **环境变量**偏向“启动配置”
- **文件写入**偏向“运行时变更”

---

## 7. 安全上是怎么考虑的？

动态注入 Flag 的核心安全点主要有四个。

### 7.1 全局密钥不进数据库

动态 Flag 依赖全局密钥 `container.flag_global_secret`。

当前代码要求它必须配置，且长度至少 32 字节；推荐通过环境变量 `CTF_CONTAINER_FLAG_GLOBAL_SECRET` 注入应用配置，而不是写进数据库或日志。

### 7.2 不用 shell 拼接写 Flag

AWD 轮换不使用：

```sh
docker exec ... sh -c 'echo xxx > /flag/flag.txt'
```

而是直接走 Docker API `CopyToContainer`，避免命令注入风险。

### 7.3 Flag 不写死在题目源码

题目镜像可以公开给教师或构建系统，但真正比赛中的 Flag 是运行时才生成的，避免“一次泄露镜像，所有实例共用同一 Flag”。

### 7.4 轮换时考虑竞态

AWD 文档里已经明确：

- 先写 Redis 中的当前轮 Flag
- 注入过程中允许上一轮短暂宽限
- 注入完成后再完全切到新轮

这是为了避免“有些队已经换新 Flag，有些队还没换完”时误判提交结果。

---

## 8. 当前实现状态下需要注意什么？

截至当前代码，动态注入 Flag 已经是**可运行能力**，但有两个现实边界要注意。

### 8.1 普通实例与 AWD 不是同一条注入链路

普通实例更偏向“环境变量”，AWD 更偏向“文件注入”。题目开发者必须明确自己的题目到底从哪里取 Flag。

如果题目只会读取 `CTF_FLAG`，但你把它放进 AWD 轮换场景下，就需要额外桥接；否则轮换后的新 Flag 不会被题目读取到。

### 8.2 当前 AWD 目标容器仍带有一期折中

文档已经说明，当前仍未完全切到“独立团队实例模型”，所以 Flag 注入和 Checker 还会按“队伍成员运行中实例”口径兜底工作。这意味着：

- 一期先保证 AWD 轮换链路打通
- 二期再把团队实例、专用网络、专用 Checker 模型收得更严谨

---

## 9. 一句话总结

这个项目里的动态 Flag，本质上是：

- 用全局密钥 + 身份信息 + nonce/轮次信息动态算出 Flag
- 普通实例在启动时通过环境变量注入
- AWD 在运行中通过 Docker API 写入 `/flag/flag.txt` 完成轮换
- 校验端再按同样规则重建或从 Redis 读取当前轮 Flag 做验证

如果你要进一步问“普通题目应该从环境变量读，还是从 `/flag/flag.txt` 读”，当前更准确的答案是：

- **练习题/普通实例：优先读 `CTF_FLAG`**
- **AWD 题：优先支持 `/flag/flag.txt`，或者自己做一层兼容桥接**

如果你进一步问“`nonce` 到底是干什么的”，可以直接把它理解成：

- 在普通实例里，它负责把 Flag 绑定到“某一次实例”
- 在 AWD 里，它负责把 Flag 绑定到“某一轮 + 某一队 + 某一题”
- 它不是密钥本身，而是让动态 Flag 具备唯一性、隔离性和可重算性的输入
